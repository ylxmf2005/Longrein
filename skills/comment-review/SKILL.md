# comment-review

## 责任边界

这个 Skill 只处理注释和日志的表达质量：判断哪里需要说明、哪里是废话、哪里已经过时，以及如何在不改变行为的前提下补充说明。它可以配合实现任务直接修改注释，但不替代 `dev` 的代码实现、`review` 的整体正确性裁决，也不因为注释问题自行重构逻辑。

开始前完整读取并应用 [`audience`](../audience/SKILL.md)。`audience` 负责目标读者、内容责任、快照检查与工作过程隔离；本 Skill 负责把这些判断落到代码证据、diff 范围、注释语义和日志约束。目标读者通常是未来维护者、调用者或值班排障者，而不是当前作者和评审现场。若相邻 Skill 不存在，先如实报告安装缺口，不凭记忆重造一份规则。

用户要求“每个函数和逻辑块都有注释”时，将它理解为：本轮新增或实质修改的函数和逻辑块都要检查是否有能让读者理解意图的注释；不要扫描未修改的旧代码并机械补齐整文件。

## 进入前先钉住范围

1. 读取目标项目和服务目录的 `AGENTS.md`，确认注释、日志、错误返回和导出符号的局部规则。默认使用中文；项目明确规定其他语言时服从项目规则。
2. 确认准确的工作树、比较基线和 `git diff`，区分新增/修改的函数与逻辑块、仅移动的代码和未触及的旧代码。
3. 先读被注释代码及其上下文，再写注释。注释必须由代码、调用契约或项目规则证明，不能把猜测写成事实。

## 注释在代码中的责任

注释主要承担两类价值：

1. **记录非显然的当前决策**：代码本身看不出的业务意图、数据权威、权限边界、时序约束、取舍和后果；
2. **给人类阅读路标**：说明函数的可观察行为，以及复杂函数中一个逻辑块或分支正在完成哪个业务阶段。

两类价值都必须落回当前代码、调用契约或项目规则。注释描述的是系统现在怎样运行、为什么必须这样运行，不是作者怎样写到这里。使用 `audience` 的快照检查和删除检查，确保读者无需 diff、MR、Prompt 或讨论记录也能理解它。

用两个问题判断一条注释是否值得存在：

- 删除它，读者是否会失去一个无法直接从代码看出的当前决策、边界或后果？
- 删除它，读者是否会失去理解复杂函数阶段或复杂分支业务含义的必要路标？

两问都是否，删除比改写更好。

## 什么值得写

优先说明代码本身看不出来、但会影响维护和排障的原因：

- 业务意图、权限边界、数据权威和返回字段的取舍；
- 复杂条件的业务含义，以及为什么某分支需要跳过、过滤、排序或降级；
- 外部调用（RPC、DB、Redis、文件或队列）的调用目的；
- `if err != nil` 分支面对的失败场景、补偿/释放/降级策略和为什么这样处理；
- 当前代码实际存在的并发窗口、状态转换、兼容期或恢复策略；
- 导出的包、类型、函数、常量和变量在语言/项目规则要求时的文档注释（Go 的导出符号尤其要检查；包注释放在包同名文件中，并以 `// Package <name> ...` 开头）。

函数头说明对调用者可见的行为与关键边界，不把函数名翻译一遍。复杂函数不能只靠函数头一句概括：校验输入、读取权威状态、执行状态转换、记录审计、补偿失败或组装结果等独立阶段，需要在进入对应逻辑块时给出短路标。简单赋值、显然的循环、标准库调用、变量名已经表达清楚的判断，以及只有一两句语句的薄包装，通常不需要注释；不要为了“每块都有”给每一行加旁白。

更多正反例见 [Good/Bad Case](references/good-bad-cases.md)。

## 修改注释的纪律

- 新增或修改代码时，只在对应的新增/修改范围补充必要注释；不要为“看起来整齐”给未触及的旧代码补注释。
- 保留已有且仍然准确的注释。只有注释与现实冲突、已经失效、重复复述代码，或会误导维护者时才删除/改写，并在交付说明中指出原因。
- 不为添加注释而重命名、拆函数、换错误处理、增加 helper、调整控制流或改变格式；如果代码本身确实需要重构，应作为独立的实现决定处理。
- 注释写当前行为、为什么、边界和后果，不要写“这一行把 A 赋给 B”这类代码旁白。不得承诺代码没有实现的锁、校验、幂等、回滚或安全保证。
- 按 `audience` 的成品边界移出开发过程、内部标签、版本对比和未落地方案。代码注释中特别禁止 `ponytail:`、`review:`、intermediate attempt、用户 Prompt、CR 对话，以及“保持 master”“这次改为”“以后可以”等依赖制作现场或未来猜测的表达；变化历史属于 commit/MR，设计缺口交给 Review/Shape。
- `Deprecated`、正在生效的兼容窗口、迁移期双写和运行时状态机可以注释，因为它们是当前系统状态；不要机械按“旧、兼容、迁移”等词删注释。
- 日志和错误信息遵守项目规范：中文日志不等于泄露底层错误、凭证或内部路径；接口错误仍使用预定义错误码/消息。注释不能掩盖未处理的 error，也不能把 `_ = err` 伪装成已处理。

## 审查流程

1. 从 diff 建立“函数/逻辑块 → 现有注释 → 当前行为/决策”的对应关系。
2. 对每个变化点标记：缺少必要说明、说明过于笼统、复述代码、过时/错误、工作过程泄漏、版本历史叙述、未落地方案、语言不符，或范围外不应改动。
3. 重新对照调用者、错误分支和项目规则证伪候选问题；无法证明的内容标成待确认，不强行写进注释。
4. 用户要求修改时，只落地请求范围内、能由代码与契约证实的注释/日志变化；再把最终代码当作没有 MR 上下文的快照冷读，确保注释无需工作过程才能成立，也没有行为变化或无关重构。
5. 至少运行 `git diff --check`；若注释修改伴随代码变化，再运行该项目对应用的格式化、静态检查或测试。不要为了验证注释新增测试文件。

评审输出应先列出有证据的问题（文件/行、读者会误解什么、建议表达），再给出保留、补充、改写或不处理的结论。没有问题时明确说明检查了哪些变化面以及仍未证明的范围。
